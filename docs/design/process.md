# 進め方

最終更新: 2026-09-10

このリポジトリの設計・開発の進め方を定める。
実装時に守るルールは [AGENTS.md](../../AGENTS.md) にある。

## 原則

**設計は ADR ベースで進める。** 実装は ADR に従い、ADR にない判断が必要になったら実装を止めて ADR を書く。

順序は次のとおり。

```
設計判断が必要 → issue で論点を立てる → ADR を PR で追加 → マージで「採用」→ 実装 issue を立てる → 実装
```

この順序を守る理由は、AI エージェントに実装を任せるため。
判断の根拠が ADR という形で残っていないと、エージェントは毎回その場の都合で判断してしまい、
設計が少しずつ崩れる。ADR は人間のための記録であると同時に、エージェントへの制約でもある。

## ADR

### 置き場所と命名

`docs/design/adr/NNNN-kebab-case-slug.md`。`NNNN` は 4 桁の連番で、既存の最大値 + 1 とする。
索引は [adr/README.md](adr/README.md)。テンプレートは [adr/0000-template.md](adr/0000-template.md)。

### 状態

| 状態 | 意味 |
| --- | --- |
| 提案 | PR で議論中。まだ従う必要はない。 |
| 採用 | 現在有効。実装はこれに従う。 |
| 却下 | 検討したが採らなかった。記録として残す。 |
| 置換 | 後続の ADR に置き換えられた。置換先へのリンクを持つ。 |

### 書くタイミング

次のすべてに当てはまるときに書く。

- 選択肢が複数あり、どれを採るかで実装の形が変わる。
- 後から変えるのが高くつく（公開 API、パッケージ構成、中間表現の形など）。
- 「なぜそうしたか」が半年後に思い出せそうにない。

逆に、局所的で後から自由に変えられる判断は ADR にしない。コード中のコメントで足りる。

### 書き方

- **却下した候補とその理由を必ず残す。** 将来の自分や他のエージェントが同じ調査を繰り返さないため。
- 外部ライブラリの調査結果には調査日を書く。バージョンや最終更新日は古くなる。
- 代償（トレードオフ）の節を省かない。採用案の欠点が書かれていない ADR は、後から見て信用できない。

### 決定を変えるとき

既存の ADR を書き換えない。新しい ADR を起こし、次の 2 つを行う。

1. 新しい ADR に、どの ADR を置き換えるかを書く。
2. 古い ADR の状態を「置換」に変え、新しい ADR へのリンクを追記する。

例外は次の 2 つ。

1. 誤字の修正や、決定内容を変えない補足の追記。
2. **その ADR に従った実装がまだ存在しない場合。** 決定そのものを書き換えてよい。
   置換の仕組みは「なぜ今この形なのか」を実装から辿れるようにするためのものであり、
   従っているコードが 1 行もなければ、辿るべき経緯が存在しない。

2 は「実装フェーズに入る前かどうか」ではなく ADR ごとに判断する。
実装がまだ触れていない ADR には、M0 が終わった後も当てはまる。

### overview.md との関係

[overview.md](overview.md) は ADR の要約ビューである。ADR を追加・変更したら overview.md も更新する。
両者が矛盾した場合は ADR が正しい。

## マイルストーンと issue

### Milestone

GitHub の Milestone を [overview.md](overview.md) の M0〜M6 に 1 対 1 で対応させる。
Milestone の説明には overview.md にある完了条件をそのまま書く。

### issue の構成

2 階層にする。

- **親 issue** — マイルストーン 1 つにつき 1 件。そのマイルストーンの完了条件を持つ。
- **sub-issue** — 作業単位。GitHub の sub-issue 機能で親に紐付ける。

エージェントに渡すのは常に sub-issue 1 件とする。親 issue を渡さない。

sub-issue の粒度は「1 つの PR で閉じられること」を目安にする。
1 PR に収まらないと分かったら、その場で分割する。

### ラベル

`area:` / `kind:` / `agent:` の 3 軸で付ける。**それぞれの軸から少なくとも 1 つ付ける。**
GitHub の既定ラベル（`bug`、`enhancement` など）は削除した。使わない。

`area:` は複数付けてよい。`kind:` と `agent:` は 1 つに絞る。
`kind:` が 2 つ必要に見えるときは、issue が 2 件分の内容を抱えているので分割する。
`agent:` を複数付けると誰が持っているのか分からなくなるため、必ず 1 つにする。

#### `area:` — どこを触るか

| ラベル | 対象 |
| --- | --- |
| `area:abstractions` | `Logora.Abstractions`。`IContentParser` / `ITemplateEngine` / `IOutputWriter` と AST の契約 |
| `area:core` | `Logora.Core`。AST の実装、パイプライン、サイト モデル、増分ビルド |
| `area:parsers` | `Logora.Parsers.*`。入力形式から AST へのマッピング |
| `area:templates` | `Logora.Templates.*`。テンプレート エンジン、Render 段階、既定テーマ |
| `area:cli` | `Logora.Cli`。`logora new` / `build` / `serve` |
| `area:docs` | `docs/` 配下のドキュメントと ADR |
| `area:build` | ビルド構成、`eng/*.sh`、CI、devcontainer、開発用のスキルなどの開発環境 |
| `area:authoring` | 記事執筆を支援するツール。Logora の利用者向けであり、本体の実装ではない |

迷いやすいところ。

- 契約と実装を同時に変えるなら `area:abstractions` と `area:core` の両方を付ける。AST ノードの追加は多くの場合これに当たる。
- コード中の XML ドキュメント コメントは `area:docs` ではない。そのコードが属する area を使う。
  `area:docs` は `docs/` 配下のファイルを触るときだけ。
- エージェント向けのスキルやプラグインは、誰のためのものかで分ける。
  Logora を開発するためのものは `area:build`、Logora で記事を書く人のためのものは `area:authoring`。
- 既定テーマはテンプレート エンジンそのものではないが `area:templates` に入れる。テーマ専用の area は作らない。

#### `kind:` — 何をするか

| ラベル | 用途 |
| --- | --- |
| `kind:feat` | 機能の追加。新しい AST ノード、新しいコマンド、新しいオプションなど |
| `kind:fix` | 不具合の修正。期待どおりに動かないものを直す |
| `kind:docs` | ドキュメントの変更。ただし ADR の追加には使わない（`kind:design` を使う） |
| `kind:test` | テストの追加・改善そのものを目的とする作業 |
| `kind:chore` | 挙動を変えない雑務。依存の更新、設定の変更、CI の調整など |
| `kind:design` | 設計判断。論点の整理から ADR の追加までを含む。アーキテクチャの意味であり、見た目のことではない |

迷いやすいところ。

- **ADR を追加する issue は `kind:design`。** `kind:docs` ではない。ADR はドキュメントの形をしているが、
  実体は設計判断であり、決めてからでないと実装に進めないため扱いが違う。
- 機能追加に付随するテストは `kind:feat` に含まれる。`kind:test` は付けない。
  `kind:test` を使うのは、既存コードのテストを後から足す場合や、テストの書き方を直す場合。
- CI の設定を変える作業は `area:build` と `kind:chore` の組み合わせになる。
  `area:build` は場所、`kind:chore` は作業の性質を表しており、軸が違うので両方付く。
- **`kind:design` の「デザイン」は設計（アーキテクチャ）の意味。見た目のデザインには使わない。**
  テーマの外観や CSS を触る作業は `area:templates` + `kind:feat` / `kind:fix` で表す。
  ただし「既定テーマをどういう形で持つか」のような、後から変えるのが高くつく判断は `kind:design` に当たる。

#### `agent:` — 誰が担当するか

| ラベル | 担当 |
| --- | --- |
| `agent:claude` | Claude。設計、ADR の起草、AST・コア・パイプラインの実装、込み入ったリファクタリング |
| `agent:copilot` | GitHub Copilot。下記 3 条件をすべて満たす issue のみ |
| `agent:human` | 人間。方針の決定、ADR の採否、マイルストーンの親 issue |

`agent:copilot` を付けられるのは次のすべてを満たすものに限る。判断できないときは `agent:claude` にする。

- 受け入れ条件が機械的に検証できる。
- 触るファイルが少なく、範囲がはっきりしている。
- 新しい設計判断を含まない。

**マイルストーンの親 issue には `agent:human` を付ける。** 親 issue はエージェントに渡さないため。

### issue に必ず書くこと

実装 issue（`.github/ISSUE_TEMPLATE/implementation.yml`）には次を書く。

- **関連 ADR** — この作業が従う ADR。該当がないなら、まず `kind:design` の issue を立てるべきかを考える。
- **受け入れ条件** — 何が動けば完了か。可能なら「このテストが通る」という形にする。

## GitHub Projects は使わない

一度ボードを作ったが、使わないことにした。進行の管理は issue のラベルと Milestone で行う。

理由は 2 つ。

1. **エージェントにとっての情報価値がない。** Status は issue の open / closed と PR の有無で分かり、
   Area と Agent はラベルの複製で、優先順位は Milestone が持っている。
   次に着手する issue は `gh issue list --label agent:claude --milestone <M> --state open` で選べる。
2. **二重管理になる。** ボードの Area フィールドとラベルの `area:` を一致させ続ける仕組みがなく、
   ずれたときにどちらが正か分からなくなる。ボードの更新を忘れれば情報が腐る。

加えて Projects はユーザー レベルのリソースであり、リポジトリ スコープのトークンでは操作できない。
Codespaces が渡すトークンでは触れないため、エージェントから扱うには
`project` スコープの PAT を別に用意することになる。得られるものに対して代償が大きい。

**誰が何を持っているかは `agent:` ラベルで見る。** 同じ area の issue を複数のエージェントに
同時に渡さないことは、下の「衝突を避ける仕組み」で担保する。

issue が数十件に増えて Milestone だけでは把握できなくなったときや、
複数リポジトリに跨るようになったときは改めて検討する。ボードは後から作っても損はない。

## 役割分担

| 担当 | 役割 |
| --- | --- |
| 人間（aetos） | 方針の決定、ADR の採否、PR のマージ |
| Claude | 設計、ADR の起草、ドキュメント AST・コア・パイプラインの実装、込み入ったリファクタリング、Copilot のレビュー指摘の裁定 |
| Copilot | PR の一次レビュー、`agent:copilot` を付けた issue の実装 |

Copilot に渡せる issue の条件は、上の「ラベル」の `agent:` の節にある。

### 工程の分離

**実装したコンテキストが、その実装のレビューを兼ねない。**
書いた本人は「なぜそう書いたか」を覚えているため、その前提を疑えない。
レビューは、書かれたコードと ADR と受け入れ条件だけを見る別のコンテキストが行う。

**テストは受け入れ条件から書く。** 実装を見ながら書くと実装した経路のテストになり、
実装の穴とテストの穴が一致する。テストが通っても仕様を満たしていない、という状態が残る。
可能なら実装より先に書く。

Claude はこれをサブエージェントで担う。定義は次の 2 つで、リポジトリに入っている。

| 用途 | 定義 |
| --- | --- |
| 実装のレビュー | [.claude/agents/implementation-reviewer.md](../../.claude/agents/implementation-reviewer.md) |
| テストの作成 | [.claude/agents/test-author.md](../../.claude/agents/test-author.md) |

レビューの観点の正は [.github/copilot-instructions.md](../../.github/copilot-instructions.md) にある。
ファイル名は Copilot 向けだが、Claude のレビュー用サブエージェントもここを読む。
Copilot の一次レビューと基準を揃え、同じ指摘が二重に出るのを避けるため。
観点を変えるときは、この 1 か所を直せば両方に効く。

**設計と実装は分けない。** ADR は「なぜ」の記録であって実装手順書ではないため、
分けると ADR に書かれていない細部の判断が実装側に落ち、往復が増える。
`Logora.Abstractions` が固まった段階で再考する。

### 衝突を避ける仕組み

- 1 issue = 1 ブランチ = 1 エージェント。同じブランチを複数のエージェントで触らない。
- 同じファイルに触る sub-issue を並行させない。並行させたい場合は依存関係を issue に書き、順に流す。
- Claude はローカルまたは worktree で作業し、Copilot はクラウド上で作業する。作業ツリーを共有しない。

## ブランチと PR

- ブランチ名は `<kind>/<issue 番号>-<短い英語スラッグ>`。
- 1 PR = 1 issue。本文に `Closes #<番号>` を書く。
- **1 PR に複数の issue を詰めない。** まとめて対応した方がよいと判断したら、PR ではなく issue の側を統合する。
  sub-issue を閉じて 1 つにするか、親 issue に受け入れ条件を集約してから、その 1 issue に対する PR を出す。
  1 対 1 を保つのは、どの受け入れ条件が満たされたのかを PR 単位で追えるようにするためである。
  分割したままでは中間状態でビルドやテストが通らない、と作業中に判明した場合もこれに従う。
- PR 本文に、従った ADR と、ADR から逸脱した点（あれば理由つき）を書く。
- マージ前の条件は次の 2 つ。
  1. CI が通っている。
  2. Copilot のレビューを受け、指摘に対応または理由を返している。
- マージは人間が行う。エージェントは自分の PR をマージしない。

### main の保護

上のルールは書いてあるだけでは守られる保証がないため、ruleset で機械的に強制する。
定義は [eng/rulesets/main.json](../../eng/rulesets/main.json) に置いてある。
Web UI だけで設定すると内容がどこにも残らず clone し直しても復元できないため、JSON をリポジトリで持つ。

**`.github/` には置かない。** あの配下は `workflows/` や `dependabot.yml` のように
置くだけで効くものが集まる場所で、効かないファイルを混ぜると適用済みだと誤解される。
ruleset をリポジトリ内のファイルから読み込む仕組みは GitHub にない。

内容は次のとおり。

- 直接 push を禁止する（PR 経由のみ）。
- force push と削除を禁止する。
- CI の成功を必須にする。
- **approve は必須にしない。** コラボレーターが 1 人であり、自分の PR は自分で approve できず、
  Copilot のレビューは approve に数えられない。必須にするとすべての PR がマージ不能になる。
- bypass する者を置かない。緊急時はルールの `enforcement` を一時的に `disabled` にする。

適用は人間が行う。`gh ruleset` は読み取り専用で、作成には `gh api` が必要だが、
`gh api` はエージェントに対して [.claude/settings.json](../../.claude/settings.json) で禁止しているため。

```sh
gh api --method POST repos/aetos382/Logora/rulesets --input eng/rulesets/main.json
```

**この操作を `eng/*.sh` のスクリプトにしない。** スクリプトにすると、エージェントが
`bash eng/...` 経由で `gh api` を実行できてしまい、deny が意味を失う。

**CI が一度も走っていない状態で適用しない。** `required_status_checks` に挙げた名前の
チェックが存在しないと、PR が永久に pending のままマージできなくなる。
先に PR を 1 つ作って CI を走らせ、チェック名が
[ci.yml](../../.github/workflows/ci.yml) のジョブ名と一致していることを確かめてから適用する。

## CI

[.github/workflows/ci.yml](../../.github/workflows/ci.yml) で `main` への push と全 PR に対して実行する。

- ビルドとテストの成否だけをブロック条件とする。
- **警告ではビルドを落とさない。** 代わりに診断 ID ごとの件数をジョブ サマリに集計して出す。
  `AnalysisLevel` が `latest-all` のため警告は多く出る見込みで、初期からエラー扱いにすると作業が進まない。
  実コードが乗って傾向が見えた段階で、エラー扱いに切り替えるかを ADR で決める。
- 書式の検査（`dotnet format`）は CI で強制しない。ローカルで `bash eng/format.sh` を使う。
- ビルド ログは artifact として残す。
- **Actions はコミット SHA で固定する。** バージョン タグは可変で、後から別のコミットを指すよう付け替えられる余地があるため。
  `<action>@<SHA> # <タグ>` の形で書き、更新するときはコメントのタグも合わせて直す。

## 開発環境

GitHub Codespaces を主開発環境とする。構成は [.devcontainer/devcontainer.json](../../.devcontainer/devcontainer.json)。

ローカル環境でも同じスクリプト（`eng/*.sh`）が動くことを保証する。
環境に依存する手順をスクリプトの外に置かない。
