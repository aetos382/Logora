# ADR-0007: 診断はデータとして扱い、渡されたシンクへ報告する

- 状態: 採用
- 日付: 2026-09-10

## 背景

パーサーやテンプレート エンジンは、処理の途中で利用者に伝えるべき問題を見つける。
パース警告、AST で表現できなかった構造（[ADR-0002](0002-document-ast.md) の `UnknownNode`）、
相互参照の解決失敗、front matter の不正、
[ADR-0004](0004-asciidoc-parser.md) の「マッピング表への記録」がこれに当たる。
これらを抽象の境界の外へどう出すかが決まらないと、`IContentParser` と `ITemplateEngine` の
シグネチャが確定せず、M1 に着手できない。

前提として、診断は Parse 段階に限らない。パイプラインは
Discover → Parse → Transform → Model → Render → Emit の 6 段階あり、
相互参照の解決失敗は Transform、front matter の不正は Model、
テンプレートの変数解決の失敗は Render で出る。
出す仕組みは全段階で同じ形であってほしい。

検討した候補は 3 つ。

1. **戻り値のデータとして返す。** 各段階が「結果 + 診断の集合」を返す。
2. **`ILogger` に流す。** CLI はログ プロバイダーとして受ける。
3. **呼び出しごとに渡されるシンクへ報告する。** 受け口を `Logora.Abstractions` に置き、
   集合の所有はホスト（`Logora.Core`）が持つ。

## 決定

**診断はビルド結果を構成するデータとして表現し、呼び出しごとに渡されるシンクへ報告する。
`ILogger` には流さない。**

### 置く型

`Logora.Abstractions` に次を置く。外部依存は増えない。

```csharp
public enum DiagnosticSeverity { Info, Warning, Error }

public sealed record DiagnosticLocation(string SourcePath, int Line, int Column);

public sealed record Diagnostic(
    string Id,
    DiagnosticSeverity Severity,
    string Message,
    DiagnosticLocation? Location);

public interface IDiagnosticSink
{
    void Report(Diagnostic diagnostic);
}
```

`record` か `class` か、`Location` を必須にするかといった細部は実装時に詰める。
決めたのは「ID と重大度と位置を持つ値」「受け口は `Report` 1 つ」という形である。
位置を特定できない診断（設定ファイル全体に対するものなど）があるため `Location` は省略できる。

### 渡し方

**`IDiagnosticSink` は呼び出しごとのコンテキスト引数で渡す。**
`IContentParser.ParseAsync` にはソース パスやオプションを載せたコンテキストが元々必要であり、
シンクはそこに同乗させる。

**コンストラクター注入で渡さない。** プラグインのインスタンスは複数の呼び出しに跨って生き得るため、
保持されると別のファイル、別のビルドの診断が混ざる。

**戻り値に診断を含めない。** パーサーが返すのは AST だけである。

### 集合の所有

**診断の集合を持つのは `Logora.Core` であり、プラグインは集合を見ない。**
次はすべて Core 側の責務とする。

- 重複排除、位置順のソート、件数の打ち切り
- 重大度による判定。`Error` があればビルドは失敗する。
  `Warning` は既定では失敗させず、`--strict` 相当の指定があるときだけ失敗させる。
  `Info` は判定に影響しない。CLI のオプション名は別途決める。
- CLI の標準出力・`serve` の画面・将来の IDE 連携への引き渡し。いずれも同じ集合を読む。

診断の件数と内容は、ログ プロバイダーの構成を変えても変わらない。

**Core は呼び出しごとに別のシンクを渡してよい。**
`IDiagnosticSink` の実装にスレッド安全性を要求しない。
将来ファイル単位で並列パースする場合、Core が各呼び出しに専用のシンクを渡して後で束ねる。

### この ADR が決めないこと

- 診断 ID の体系（`LGxxxx` のような連番か、名前空間付きの文字列か）。
- メッセージ本文のローカライズと、ID から本文を引く仕組み。#6（resx）と重なる。
- 開発者向けログの有無。Logora 自身の内部動作を `ILogger` に出すかは
  [#8](https://github.com/aetos382/Logora/issues/8)（DI の採否）と一体である。
  この ADR が禁じるのは「診断をログに載せること」だけである。

## 理由

### 診断をデータとして扱う理由

**診断は利用者向けの出力であり、開発者向けのログとは別物である。**
前者はビルドの成果物に対する評価で、消費者は記事を書いている人である。
後者は Logora の動作の記録で、消費者は Logora を開発・運用する人である。

**候補 2（`ILogger` に流す）を却下した理由は 4 つある。**

1. **`IsEnabled` で診断が消える。** ログ プロバイダーの設定次第で件数が変わるチャネルに乗せると、
   「警告があればビルドを失敗させる」という判定をそこに置けない。
   ビルドが成功するかどうかがログの構成に依存するのは、あってはならない。
2. **集合として扱えない。** 重複排除、位置順のソート、件数の打ち切りができない。
   ログは 1 件ずつ流れるもので、全体を見渡す操作を持たない。
3. **保持に向かない。** `serve` は「前回のビルドの診断一覧」を画面に出す必要がある。
   ログはストリームであり、診断は結果の集合である。
4. **型付きで受け取れない。** 消費者がログのスコープや state を掘って診断を復元するのは無理筋で、
   IDE 連携のような機械的な消費者を作れない。

### 戻り値ではなくシンクにした理由

候補 1 と 3 はどちらも診断をデータとして扱い、上の 4 点を満たす。
そのうえで候補 3 を採った理由は 4 つ。

1. **包み型が段階ごとに増えない。** 候補 1 では「AST + 診断」「サイト モデル + 診断」
   「レンダリング結果 + 診断」と、6 段階それぞれに包み型ができ、
   段階を繋ぐたびに集合を取り出して合流させるコードが要る。
   候補 3 なら戻り値はその段階の成果物だけで済む。
   コンテキスト引数は他の理由（ソース パス、オプション）で元々必要なので、新しい型は 1 つも増えない。
2. **中断しても失われない。** プラグインが例外を投げた場合、戻り値方式では
   それまでに積んだ診断がまとめて消える。「3 件の問題を見つけた後で落ちた」を報告できない。
   報告済みの診断はホスト側にあるので、候補 3 ではそのまま残る。
3. **打ち切りをホストに置ける。** 壊れた入力に対して診断が数万件になり得る。
   候補 1 ではプラグインが際限なく積んだ集合を受け取ってから捨てることになり、
   メモリのピークを抑えられない。候補 3 なら上限に達した時点で捨てられる。
4. **プラグインが集合を持たない。** 他のプラグインが出した診断を読んだり書き換えたりする余地がない。

**候補 1 を却下した理由。**
戻り値だけを見れば済むので純粋で、テストも書きやすい。この点は候補 1 の方が良い。
それでも上の 4 点、特に 1 と 2 が重い。テストのしやすさは、記録用のシンク実装を
テスト側に用意すれば埋まる程度の差である。

## 代償

- **シンクは副作用のある引数である。** プラグインのメソッドは戻り値だけを見れば分かる関数ではなくなり、
  テストには記録用のシンク実装が要る。候補 1 を捨てて引き受けたのはこの点である。
- **報告した側は結果を知らない。** プラグインは自分の診断が打ち切られたのか、
  重複として捨てられたのかを知らない。`Report` は成否を返さない。
- **保持の禁止を機械的に防げない。** プラグインがコンストラクターでコンテキストを受け取って
  フィールドに置いてしまう可能性は、規約で禁じるしかない。
  レビューの観点（[.github/copilot-instructions.md](../../../.github/copilot-instructions.md)）に載せる。
- **`Report` が同期メソッドである。** `serve` の画面へ逐次流すような非同期の消費者を後から足すには、
  Core 側でバッファーを挟むことになる。
- **診断を保持するのでメモリに乗る。** 打ち切りの仕組みが必要になる。ログなら流して捨てられた。
- **開発者向けログを別に出すなら経路が 2 つ並ぶ。** 同じ事象が両方に現れる余地があり、
  どちらに出すべきかの判断がその都度必要になる。境界は「利用者が直せる問題か」で切るが、
  機械的な判定ではない。
- **ログ基盤が持つ機能を自作することになる。** 出力先の切り替えや整形は Logora 側で書く。

## 影響

- `Logora.Abstractions` に `Diagnostic` / `DiagnosticSeverity` / `DiagnosticLocation` /
  `IDiagnosticSink` が入る。外部依存は増えないため、
  [許可リスト](../abstractions-dependencies.md)には影響しない。
- `IContentParser` と `ITemplateEngine` はコンテキスト引数を取る形になる
  （[ADR-0003](0003-pluggable-components.md)）。M1 の実装はこの形から始める。
- [ADR-0002](0002-document-ast.md) の `UnknownNode` と
  [ADR-0004](0004-asciidoc-parser.md) のマッピング表への記録は、この診断を行き先とする。
- `Logora.Abstractions` が `Microsoft.Extensions.Logging.Abstractions` に依存する動機のうち、
  診断に由来するものは消えた。残るのは DI の採否
  （[#8](https://github.com/aetos382/Logora/issues/8)）だけである
  （[ADR-0006](0006-abstractions-dependencies.md)）。
- 診断 ID の体系とローカライズは #6 と合わせて別に決める。
