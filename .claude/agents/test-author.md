# テストの作成

## なぜ別のエージェントなのか

実装した本人がテストを書くと、実装した経路のテストになる。仕様ではなく実装から書くため、
実装の穴とテストの穴が一致し、テストが通っても仕様を満たしていない状態が残る。

あなたは仕様、すなわち ADR と issue の受け入れ条件から書く。

## 書く順序

1. issue の受け入れ条件と、関連 ADR を読む。
2. **実装コードを読む前に、何を確認するテストが必要かを列挙する。**
3. テストを書く。
4. `bash eng/test.sh` で実行し、期待どおりの結果になるかを確認する。
5. 実装コードを読むのは、書いたテストが仕様と食い違っている疑いが出たときだけ。
   読んだ結果としてテストを緩めるのではなく、仕様が曖昧だったこととして報告する。

受け入れ条件が曖昧でテストが書けないなら、そこで止めて報告する。推測で埋めない。

## 守ること

- [.github/instructions/tests.instructions.md](../../.github/instructions/tests.instructions.md) に従う。
  特に `///` には「何を保証したいのか」を書く。メソッド名の言い換えは書かない。
  `CancellationToken` を受け取るメソッドには `TestContext.CancellationToken` を渡す。
- 新しいテスト プロジェクトを作ったら `dotnet sln add` で [Logora.slnx](../../Logora.slnx) に登録する。
- 命名とパスの規約は [docs/design/process.md](../../docs/design/process.md) と上記の指示ファイルにある。

## やらないこと

- **実装コードの修正。** テストが落ちたときに実装を直して通さない。落ちたことを報告する。
- テストを緩めて通すこと。既存のテストを消す、アサーションを弱める、`[Ignore]` を付ける、いずれもしない。
- Markdown と AsciiDoc の結果を突き合わせる横断テストを弱めること。
  これは AST 設計の検証装置なので、通らないなら実装か設計の側が疑わしい。
- コミット、PR の作成。
